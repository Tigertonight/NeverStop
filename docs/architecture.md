# MVP 技术架构

## 产品边界

第一阶段只覆盖跑步与游泳，输出非医疗性质的动作观察、能力提升建议和历史对比。健身动作、登录体系、真实设备授权和复杂训练计划不进入首版闭环，但保留扩展位置。

## 分析流水线

```text
视频上传
  -> 格式校验与转码
  -> 镜头质量检查
  -> 关键帧 / 动作周期切分
  -> 姿态关键点估计
  -> 运动专项指标计算
  -> 规则与置信度判断
  -> 证据帧渲染
  -> 大众化报告生成
```

Pillow / OpenCV 属于“证据渲染层”：根据结构化分析结果画关键点、角度、箭头和标签。它不负责决定动作是否有问题。这样同一份分析结果既能生成图片，也能被 H5 的交互证据层和历史对比复用。

## 推荐服务划分

- `web-app`：当前 React H5，处理上传体验、报告阅读和历史对比。
- `api`：FastAPI，负责上传凭证、分析任务、报告和运动记录 API。
- `analysis-worker`：FFmpeg、OpenCV、MediaPipe / MoveNet；后续按游泳难度引入 MMPose。
- `insight-engine`：专项指标、规则、置信度和建议模板；LLM 只做表达优化，不直接凭视频猜结论。
- `evidence-renderer`：Pillow / OpenCV，把结构化证据渲染为可分享图片。
- `storage`：对象存储保存原视频、抽帧和渲染图；PostgreSQL 保存任务、指标、洞察和训练记录。

## 前后端契约

前端契约定义在 `src/lib/contracts.ts`：

- `VideoAnalysisGateway` 隔离当前模拟流程与后续真实 API。
- `AnalysisJob` 支持排队、预处理、姿态识别、报告生成和失败状态。
- `WorkoutImportPayload` 以统一训练会话加时序样本承接 Apple Health、Garmin、Health Connect 和文件导入。
- 原始 FIT / GPX / TCX 文件只保存引用，标准化数据单独入库，避免丢失供应商特有字段。

## 数据同步原则

1. 用 `provider + externalId` 幂等去重。
2. 所有时间存 UTC，同时保存原始时区。
3. 距离统一存米、时长存秒，展示层再转换单位。
4. 高频心率、配速、步频、GPS 使用时序样本，不塞进训练主表。
5. 保留原始文件或供应商 payload 引用，适配升级后可重新解析。
6. Keep 暂按文件 / 授权占位，不依赖非公开接口。

## 下一实现阶段

1. 建立 FastAPI 上传与异步任务骨架。
2. 用 MediaPipe 跑通跑步侧面视频的关键点 JSON。
3. 先实现 3 个高解释性跑步指标：身体前倾、触地点相对髋部位置、左右周期稳定性。
4. 接入 Pillow 证据图渲染，并让 H5 从真实报告 JSON 读取数据。
5. 再针对水面遮挡、反光和摄像机角度建立游泳数据集与指标基线。
